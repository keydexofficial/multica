  二、桥接核心（claudemanagedruntime）

  这是我读得最细的部分，它的设计与 OMA 高度同构：

  协议层（http.go）
  - DefaultAnthropicURL = https://api.anthropic.com/v1（:19），固定 anthropic-version + anthropic-beta: managed-agents-2026-04-01（:93），Authorization: Bearer。
  - newClient 只允许 HTTPS，loopback 例外（:96-102）。
  - 错误体只用于探测 "需要 workspace-scoped key"（:43-54），从不回显 body。
  - 有 Retry-After 解析与 429 退避。

  会话流程（bridge.go）
  - createSession 把 prompt 作为 initial_events 一次提交（:500），成功即 running + Started。
  - 歧义创建恢复：findCreatedSession 用 GET /sessions?agent_id=&created_at[gte]=&order=desc&page= 按 multica_task_id 匹配（:538-568），最多 10 页；找不到且已重试过一次则失败。
  - 提交歧义不重发：先写 sending 意图（:443-448），deadline 后只报"需人工检查"。
  - 续用：continueSession 要求 prior session idle、agent/environment 一致、资源指纹一致、无其他 run 占用（:650-680）。
  - 取消：Anthropic 无 cancel，user.interrupt + 轮询 idle/terminated，最多 3 秒（:688-735）；未完成的清理进入 durable queue。
  - 清理：Unresolved 记录"可能已创建但查不到"的会话，跨重启保留；resolveUnresolved 每 tick 重试（:817-846）；ErrCleanupUnauthorized 会终止 supervisor 并置 error。
  - 交付：/complete 带 output，/fail 带 error + failure_reason="claude_managed_execution"（:772-790）。
  - 没有 usage、chat、leader、quickcreate、reply files、attachments。

  事件映射（events.go）
  - 轮询 page 游标 + created_at[gte] 回退；用 processed_at 处理同时间戳事件；queued 事件不推进游标（:44-77）。
  - 映射：agent.message→text、agent.tool_use/mcp_tool_use→tool_use、agent.tool_result/mcp_tool_result→tool_result、session.error、session.status_idle（end_turn=成功，其余=failed）、session.status_terminated/deleted（:107-150）。
  - 每条消息带 seq + idempotency_key = "claude:"+eventID。

  Prompt/资源（prompt.go）
  - 只支持 issue run；拒绝 chat/leader/attachments/本地目录/skills/custom env/args/mcp/model（:18-33）。
  - 资源：只允许 HTTPS github.com、单仓库、branch checkout（:88、:151-166）；authorization_token 只存在于请求副本，不写 journal（credentials.go）。
  - 要求分支名包含 issue identifier，便于 Multica GitHub 集成回链（BranchName）。

  状态（state.go）
  - journal 含 runs/cleanup/unresolved；严格 phase 校验；原子写 + 文件锁；不存凭据。

  目录（catalog.go）
  - 校验 agent_/env_ 前缀，分页最多 10 页，只返回 id/name。

  测试：约 40 个场景，覆盖歧义提交/创建、重启恢复、取消、限流、并发、续用指纹、vault、工具调用 ID、journal 持久化、目录分页、错误脱敏。local_integration_test.go 用真实 Multica router + 假 Anthropic HTTP 服务端，端到端建
  runtime/agent/issue。这套测试骨架几乎可以原样给 OMA 用。

  三、连接层与 supervisor（claude_connection.go / claude_disconnect.go）

  - 每个 workspace 一条 cloud_agent_connection（provider=claude_managed），配置加密，含 AnthropicToken/GitHubTokens/VaultIDs/MulticaToken。
  - 服务端 supervisor：pg_try_advisory_lock(71243, 8192) 选主；每 5 秒对账 revision；busy_until + acquireClaudeStep 串行化每个 tick；token 每小时续期，owner 降级/停用即吊销。
  - 启动时构造 claudemanagedruntime.Config，journal 存 DB 加密列；OnReady 把 runtime 设为 public 并置 online。
  - 连接页操作：save（保持暂停）、resume、check、stop、disconnect。disconnect 顺序：停桥 → 取消远端会话 → teardown runtime → 解绑 agents → 删连接。
  - 关键细节：Anthropic base URL 被写死。CheckClaudeConnection、ListClaudeAgents、cleanupClaudeJournal 都直接用 DefaultAnthropicURL（claude_connection.go:22-25 注释明确"base 固定"）。这是 OMA 必须改的第一处。

  七、必须先解决的 PR1 结构性问题

  这是读完代码后最值得强调的：

  1. 连接/监督/断开层是复制粘贴：claude_connection.go 与 qoder_connection.go 相似度约 67%，claude_disconnect.go 与 qoder 版约 42%，bridge.go 约 52%。再加 OMA 就是第三份。建议在 OMA 之前先抽 cloudagent 通用连接层 + provider
  descriptor（settings 结构、SQL 条件、bridge 构造、prefix、服务名、能力位），三个 provider 只提供描述符。否则重复代码门禁（3.75%）和后续维护都会恶化。
  2. Anthropic base URL 写死在 handler，与 standalone 可配置的行为不一致；OMA 必须把它变成连接配置的一部分。
  3. provider 列表散落在 SQL 与前端常量中（IN ('qoder_cloud','claude_managed')、CLOUD_AGENT_PROVIDERS、多处 === "claude_managed"），这是 OMA 最容易漏改的地方。
  4. 没有 usage 上报；PR1 README 的 Known limits 明确列出。OMA 需要补，且要处理续用会话的基线，避免重复计费。
  5. 能力位靠 if/else：chat/quick-create/skills/attachments/tool approval 都是零散判断。建议在 provider descriptor 里定义 capabilities，前后端共用。
